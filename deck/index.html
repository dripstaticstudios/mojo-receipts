The idea · 3 of 3

Exact search that repairs instead of rescanning

The incremental thesis: split a corpus into blocks, cache each block's best results, and when something changes, recompute only the touched blocks and merge — instead of rescanning everything.

  • Exact, not approximate: every repair is checked against a brute-force full scan.
  • The question is where it stops paying: repair cost grows with the number of touched blocks; a full scan stays roughly flat. The crossover slide measures exactly where they meet.

Scale · The same repair at a million passages — native Mojo, real text

Exact repair for sparse edits. At 1,000,384 passages.

One edit lands and the answer repairs instead of rescanning: 5.09 ms at a million passages, against a 926 ms full rescan. At 100,224 passages the same repair is 0.58 ms (scan: 88 ms); eight sparse edits cost 5.62 ms / 1.08 ms. Every trial was refereed by a fresh full scan — 32 / 32 exact, top-10 identical, max score delta 0.0. The edits are real text, and the clock includes turning each edit into a vector — about 26 µs per passage — the cost a pre-made-vector benchmark never pays.

Where it loses: touch half the blocks and the total blows the 50 ms cutoff at both scales — 72.9 ms at 100K, 748.6 ms at 1M. Embedding is 38% of the 100K broad total; repair alone (45.5 ms) would have passed. At 1M broad, repair still beats rescanning — but thin. And a brand-new query costs a full cache build: 92.5 ms / 889 ms.

The honesty slide

Attempt 1 failed — and the record kept it

104 / 150 batches matched. Gate failed.

  • Root cause was the test harness, not the design. The edit formula (i*13 + j*29 + salt*7) % 29 makes the j-term vanish (29j ≡ 0 mod 29), so every edited vector was constant across dims.
  • One edit made an exactly-zero vector. Its cosine is NaN, and NaN breaks the total order inside insertion — repair and scan diverged. The cache audit was blind to it, because NaN − NaN comparisons are false.
  • Fix: edit formula changed to the base formula's family, (i*7 + j*11 + salt*5) % 23 − 11) / 11, which varies over j and cannot produce a zero vector.
  • Result: 150 / 150 in both languages. The failed sources are preserved in the repo — failures stay in the record. That's a feature of the program, not a footnote to hide.

Failed sources preserved: kernels/incremental_search_attempt1.{mojo,cpp}. Passing receipts: incremental_search-mojo-61164680 · incremental_search-cpp-6679e92c.

Honest warts — printed, not hidden

Where the usual stack wins, and where the design breaks even

  • C++ repair is faster at small edit counts. At T=1: C++ 8,208 ns vs Mojo 14,538 ns. The fixed merge dominates at low edit counts, and C++'s small-vector handling beats Mojo's List allocation pattern in this implementation. The gap narrows as T grows; at T=64 the two are indistinguishable (196,301 vs 194,156 ns).
  • Repair degenerates at T=64. Touching every block, repair costs ~1.27× a full scan in both languages — it becomes rebuild everything plus a merge, and the merge overhead is the entire penalty.
  • One machine, one compiler version, shared-VM noise. Mojo full-scan readings ranged 123,242–155,304 ns across levels for identical work. Crossover points (≈48 and ≈51 blocks) are interpolations between measured levels, not direct measurements.
  • Scope. Every number in this deck is per-receipt — one task, one machine, one compiler version. None of it is a universal claim about Mojo or C++.

On Java: No Java column exists — not because Java lost, but because no verified Java run was ever produced for this table; this deck only prints what a receipt proves.

The takeaway

The win is the design, in both languages

Mojo took the kernel bouts — softmax ~6%, embed search ~1.34×, fused ~1.18×. But the deeper result is language-independent:

Repair, don't rescan —
exactly, and provably.

Up to half the corpus edited, repair is strictly cheaper than a full scan in both engines, with results verified exact batch by batch. A compiled engine room makes that design usable from a web page and a chat — with a receipt attached to every claim.
